Building software with Anthropic's tools

A short guide to Claude and Claude Code for a solo developer who sets the requirements and lets agents write, test and ship the code. It explains each idea in a page or two, shows where it fits in your setup, and then tells you which page of Anthropic's documentation to read next, and what to look for there.

Chapter 1

Who's who: Claude, the apps, Claude Code, and Perplexity

Claude is the model, the thing that reasons and writes. You reach it through several products. The Claude apps (web, desktop, iPhone and iPad) are for conversation. Claude Code is an agent: it works inside a code repository, reads and edits files, runs commands and tests, and hands back changes. The Claude Platform is the API for developers who build on Claude.

Claude Code is one agent that you can reach from several places: the terminal, the desktop app, the web at claude.ai/code, and the Code tab in the Claude mobile app. Wherever you start it, the agent itself is the same.

In your setup

You already use two agents. Perplexity Computer is strongest at research, conversation, and writing up concepts, processes and requirements, and it works well from the iPad. Claude Code is strongest inside a repository: it codes, runs tests, and keeps working until the checks pass. Neither one remembers the other's conversations. They only share what's committed to GitHub. That's why your architecture and rules live in repository files rather than in either tool's memory.

Why can't Perplexity Computer and Claude Code share what they learn just by talking to you?

They don't share memory. What one agent learns in a conversation stays with it. The only thing both can read is the repository, so decisions they both need have to be committed there: in AGENTS or CLAUDE files, the standards and ADRs.

Chapter 2

How an agent works

An agent runs a loop. It gathers context by reading files and searching, then it acts by editing, running commands or calling tools, then it checks the result. It repeats until the task is done or it needs you. The model's reasoning only ever covers what's in its context window: your request, the files it has read, the tool output, and the standing instructions loaded at the start.

That leads to the most important idea in this guide. The quality of the agent's work depends on its context. Clear goals, a way to check the result, and the right rules loaded at the right time matter more than clever prompts.

In your setup

This is why you write requirements with acceptance criteria and keep CI strict. A requirement with a test to pass gives the agent a "check the result" step it can actually run. Without one, the agent stops when the work looks done, not when it is done.

A task finishes but the result is wrong, and the agent reported success. What was most likely missing?

A way to check the result: a test, a script or explicit acceptance criteria. Without one, the agent's "check the result" step is only its own opinion.

Chapter 3

Working from the iPad: cloud sessions

A cloud session runs Claude Code on Anthropic's machines, not yours. You start it from claude.ai/code or the Code tab in the Claude app. The session clones your GitHub repository, does the work, and pushes a branch, and you can open a pull request from it. The session keeps running after you put the iPad down, and you can check on it or steer it from any device.

In your setup

This is your main way of working. Write or approve an issue (often with Perplexity Computer), start a cloud session against the app repository from the iPad, and review the pull request it produces. When something needs a real machine, such as a native build or a local device test, teleport the session to the Mac and carry on. Connecting through the Claude GitHub App is required for Auto-fix, which watches a pull request and fixes CI failures and review comments.

Know the limits

Cloud sessions are available on Pro, Max, Ultra and Team plans. They share your plan's usage limits. They can expire after a period of inactivity: the conversation comes back, but background work that was still running doesn't. The session clones your branch from GitHub, not your local copy, so push any local commits first.

Try it

On the iPad, start a cloud session on a small app repository and ask: "Read the repository and tell me how it's tested, without changing anything." Then ask for a one-line documentation fix and turn it into a pull request. Watch CI run on it.

You made a local commit on the Mac and then started a cloud session from the iPad. The session doesn't see your change. Why?

Cloud sessions clone the branch from GitHub, not your local checkout. Push first, then start the session.

Chapter 4

Giving it your rules: memory and instruction files

Claude Code loads standing instructions from files in the repository at the start of every session. The main one is CLAUDE.md. You can also put rules for specific topics in .claude/rules/, and give a rule a paths filter so it only loads when matching files are touched. A CLAUDE.md can pull in other files with @path/to/file. Separately, auto memory lets Claude save its own notes as it works.

Your setup needs this

Claude Code reads AGENTS.md, but by default only when there's no CLAUDE.md. Your apps use AGENTS.md, generated from templates/AGENTS.application.md. The safe pattern is a one-line CLAUDE.md that contains @AGENTS.md. Then both agents read the same file, and adding a CLAUDE.md later can't silently hide your rules.

In your setup

Each app repository already has the right files: AGENTS.md, docs/CODING-STANDARDS.md, docs/EXCEPTIONS.md and STANDARDS-ADOPTION.json. Claude Code just needs a route into them. Keep CLAUDE.md short and point it at those files. Use path-scoped rules for things like "tests in this folder follow these conventions." Don't copy standards text into memory files; link to it, so one standards release can update every app.

Read now
  1. How Claude remembers your projectLook for: the AGENTS.md rule, @ imports, .claude/rules/ with paths, and auto memory.
  2. Best practices for Claude CodeHow Anthropic itself writes instruction files and structures tasks.
An app has both AGENTS.md and a new CLAUDE.md that someone added for a quick note. What happens to your standards?

By default Claude Code stops reading AGENTS.md, so your standards drop out of its context without any warning. The fix is to have CLAUDE.md import @AGENTS.md, or to change the project-instructions setting to read both.

Chapter 5

Extensions: skills, subagents, hooks, connectors, plugins

Claude Code has five ways to extend it. Each does a different job and costs a different amount of context. Choosing the right one for each job is most of the skill.

PieceWhat it isWhen it loadsUse it for
CLAUDE.md / rulesStanding instructionsEvery sessionShort, always-true project facts
SkillA packaged procedure in SKILL.md, with a descriptionOnly the description at first; the full skill when it's relevant or you type /name"How we write a release note," "how to add a unit"
SubagentA specialist with its own instructions, tools and modelWhen it's started, in a fresh contextReviewer, test writer, auditor: work you want kept separate
HookA command that runs at a fixed point, such as before a tool runs or after a file is editedWhen that event happens; costs no contextEnforcement: things that must hold every time
MCP serverA connection to an outside service or toolTool names at start; full details when usedGitHub, databases, other services
PluginA versioned package of the aboveWhen it's enabledSending the same set to every app

The key distinction: skills and instructions guide the agent, hooks enforce on it. A PreToolUse hook runs before an action. If it exits with code 2, the action is blocked, and the message it printed goes back to Claude so it can correct course. The model can't talk its way past a hook.

In your setup

Sort your standards by how strict each rule is. "Never write outside the app's data layer" or "no secrets in commits" should be hooks. "How to structure a delivery profile" should be a skill. "Review this change against the architecture" should be a subagent running on Opus. Approved exceptions recorded in docs/EXCEPTIONS.md become input that the hooks check, so an approved exception is allowed rather than blocked.

"Never commit a secret" and "how to write a release note": which extension does each one need?

"Never commit a secret" needs a hook, because it must hold every time whatever the model decides. "How to write a release note" needs a skill, because it's a procedure loaded when it's relevant. Both can ship in one plugin.

Chapter 6

Choosing a model

Models trade capability against speed and cost. Your rule of thumb: Sonnet for routine work, Opus for design and review, and Fable for rare checks across everything. In Claude Code you can set the model in four places:

WhereHowTypical use
Per session/model or --modelSwitching up for a hard problem
Plan, then buildopusplan: Opus while planning, Sonnet while carrying out the workEngineering tasks with design up front
Per subagentmodel: field set to sonnet, opus, fable, a full model ID, or inheritReviewer on Opus, implementer on Sonnet
In CIclaude_args: "--model …" in the GitHub ActionPinning the model so CI results are reproducible
In your setup

Set the model on each subagent, not just per session. A subagent set to inherit uses whatever model the main conversation is on, so an "Opus for this one question" moment can carry over to routine helpers. Writing model: sonnet or model: opus into each subagent's definition makes the tier part of the role, and it's committed to the repository where you can review it.

  2. Models overviewThe current lineup. Check it whenever the model names change.

You want design on Opus and the code written on Sonnet in one task. What's the simplest way?

Use opusplan. Plan mode runs on Opus, and when you approve the plan, carrying it out switches to Sonnet.

Chapter 7

Review and CI

Agent-written code earns trust the same way anyone's code does: automated checks, an independent review, and an owner who approves. Anthropic offers two tools for this on GitHub.

ToolWhat it doesNote
Claude Code GitHub Action
anthropics/claude-code-action@v1		Responds to @claude in issues and pull requests, or runs a fixed prompt on any GitHub eventSet up with /install-github-app. Pin the model in claude_args.
Code ReviewSeveral agents review each pull request and post inline comments ranked by severity, guided by REVIEW.mdTeam and Enterprise plans only. Its check run never fails the build; it advises.
In your setup

CI stays owned by the repository. Your existing required checks are what block a merge. Claude is an additional reviewer and fixer, not the thing that decides. On a personal plan, use the GitHub Action with a review prompt and an Opus reviewer subagent. Add Code Review only if you move to a Team plan.

Your repository's CI checks and you. Claude's review comments inform the decision; required checks and your approval make it.

In your setup

The thread running through the whole lifecycle is stable IDs. Concept items (CON-) are referenced by process steps (PROC-01.S3), which are referenced by requirements, which are referenced by acceptance tests. Claude Code can follow those IDs because they're in the repository. That's what lets a business-process test trace back to the process document it checks.

Why do the first five stages lean on Perplexity rather than Claude Code?

They're research, conversation and writing, not repository work. Claude Code is strongest when there's code to run and check. What the early stages produce, committed as files and issues, becomes the context Claude Code works from later.

Chapter 9

The standards plugin

A plugin packages skills, subagents, hooks and connections into one installable unit with a manifest (.claude-plugin/plugin.json) that can carry a version. It's distributed through a marketplace, which is just a catalog file (.claude-plugin/marketplace.json) in a repository, not a hosted store. Installing a plugin for a project records it in the committed .claude/settings.json, so everyone who works in that repository gets it enabled.

Plugin evals test whether the plugin actually changes Claude's behavior. Each test case is a realistic prompt plus checks on the result: a pattern match, whether a tool was used, tool order, whether a file exists, or a judgment by another model. claude plugin eval runs every case with and without the plugin. It exits with 0 if every case reaches the threshold and 1 if any falls short, and that exit code is what blocks CI.

In your setup

The plugin's version matches the standards tag, such as standards-1.1.0.0 and plugin 1.1.0.0, and the release note explains what changed, as you already require. Apps adopt it explicitly, the same way they pin a standards release now: the adoption record and the project settings name the same version. The standards repository's CI runs the evals and refuses to tag a release that fails them. A batch run across all apps can then report which ones are behind.

The plugin passes its unit tests but the agent still ignores one rule. What catches that?

An eval. Unit tests check the plugin's code; evals run the agent with the plugin installed and check whether it actually follows the rule.
